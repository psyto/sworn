## BLOCKER

- **AC-Z4 is impossible/underspecified as written.** Four digest fields are not `verify` calldata: `parentChainId`, `verifier`, `verifierConfigHash`, and `chainSpecHash` are respectively immutable/derived. “Each of the 19 digest inputs mutated” therefore cannot be satisfied by argument mutation alone. Require explicit same-vkey clone tests with changed `PARENT_CHAIN_ID` and `PINNED_CHAIN_SPEC_HASH`, and a test proving config-hash enforcement. Otherwise a contract can omit an immutable binding and still meet the described argument-mutation tests. Verified: [spec:33-58](docs/specs/003-zone-verifier.md:33), [spec:82-90](docs/specs/003-zone-verifier.md:82), [spec:108-112](docs/specs/003-zone-verifier.md:108).

## MAJOR

- **The acceptance tests do not establish guest-side semantic binding of all public inputs.** AC-Z4 catches a contract that ignores a calldata field: unchanged proof + mutated field still verifies. But it does not catch a guest/SPF regression where a public input is merely hashed and passed through rather than checked during execution. AC-Z1 only negatively tests a deposit amount. Add guest/native negative tests for every `PublicInputs` member against the unchanged config/witness, and assert rejection (or an explicitly justified expected behavior). Verified SPF currently checks parent-chain/zone through configured chain ID, final Tempo block and anchor, and withdrawal index: [lib.rs:37-53](spikes/zone-spf/zones/crates/spf/src/lib.rs:37), [lib.rs:297-317](spikes/zone-spf/zones/crates/spf/src/lib.rs:297). The six inputs are defined at [types.rs:55-75](spikes/zone-spf/zones/crates/spf/src/types.rs:55).

- **No-domain EIP-712 leaves destination-chain replay open.** `parentChainId` is the source/dev chain (explicitly 1337), not `block.chainid`; `verifier` only separates deployments by address. A same-address deployment with the same immutables/vkey on another chain can accept the same proof. This is especially relevant because the verifier is deployed on Moderato but commits a dev-chain parent ID. Add and enforce a destination chain ID in the struct (or a normal EIP-712 domain), or explicitly list this as D4 and prohibit cross-chain security claims. Verified: [spec:33-34](docs/specs/003-zone-verifier.md:33), [spec:76-80](docs/specs/003-zone-verifier.md:76). Inferred: identical contract addresses/configurations can occur across EVM chains.

- **`keccak256(genesis_bytes)` is a sound cryptographic pin to an exact input artifact, including hardfork JSON, but not proof that it is the authentic/correct chain spec.** The guest hashes before parsing, and the contract pins the same hash, so changed bytes cannot be substituted absent a Keccak collision. But the name `chainSpecHash` overstates it: formatting and irrelevant genesis fields alter it, while constructor selection remains a trusted ceremony. The “untouched alloc changes it” criterion demonstrates this artifact binding. State this limitation in “may not claim” and require recording the exact genesis artifact/hash. Verified: [spec:56](docs/specs/003-zone-verifier.md:56), [spec:64-68](docs/specs/003-zone-verifier.md:64), [spec:101-102](docs/specs/003-zone-verifier.md:101).

## MINOR

- The 19-field struct is unambiguous: all fields are static ABI types, ordered and typed explicitly; `alloy sol!` has precedent for the 18-field Nitro struct and hashes it with `eip712_hash_struct`. A literal canonical type-string/typehash test vector should be specified, not merely “identical in both,” since two implementations can share the same erroneous string. Verified: [protocol.rs:13-38](spikes/zone-spf/zones/crates/prover/src/protocol.rs:13), [protocol.rs:122-143](spikes/zone-spf/zones/crates/prover/src/protocol.rs:122), [spec:103-104](docs/specs/003-zone-verifier.md:103).

- D1–D3 are candid but incomplete: add destination-chain replay and the trusted genesis-pin ceremony to deviations/“may not claim.” D2 is materially safe only for this write-nothing demonstration; it would be unsafe to generalize to settlement. Verified: [spec:88-95](docs/specs/003-zone-verifier.md:88), [spec:114-125](docs/specs/003-zone-verifier.md:114).
